workflow/rules/02d_riboseq_transcriptome_filter.snake (new; rewritten
2026-10-16 after a real bug found on the first real run)
    - FIRST ATTEMPT (wrong): rule transcriptome_mapq_filter applied the
      SAME samtools filter used for the genome BAM (CMD_PARAMS["samtools"],
      e.g. "-bF4q10") to STAR's Aligned.toTranscriptome.out.bam, on the
      (plausible-looking, but WRONG) assumption that STAR's MAPQ encodes
      transcript-level NH the same way it does for the genome BAM. On the
      real first run this produced gene-level sums ~2x HIGHER than plain
      featureCounts -- backwards for a stricter filter. Root-caused by
      direct inspection: among 500,000 real "MAPQ>=10-surviving" records,
      NH values ran up to 830+ and the same read name appeared ~7.3x on
      average (-q10 did not reduce the record count AT ALL vs. the fully
      unfiltered file -- 139,839,644 records either way, confirmed). STAR
      evidently computes MAPQ differently (decoupled from NH) in
      --quantMode TranscriptomeSAM output than in the genome BAM.
    - REAL FIX: rule transcriptome_multimap_filter instead reuses
      multimappers2.py (workflow/scripts/multimappers2.py -- the same
      script the genome BAM's align_filter_multimap rule would use if
      CMD_PARAMS["multimap"] were ever set, though it's empty in this
      project's real config so that branch has never actually executed).
      Groups alignment records by QNAME (qname-sorted input) and keeps at
      most -k 1 per read, regardless of what MAPQ means for a given BAM --
      this is what actually guarantees one alignment record per surviving
      read (confirmed on real data: filtered record count == distinct read
      name count exactly, 7,072,732 == 7,072,732 for ribo_untr_a). Also
      found in passing: the existing align_filter_multimap rule's
      multimap-enabled branch references "pipelines/multimappers2.py",
      which doesn't exist in this repo (real path:
      workflow/scripts/multimappers2.py) -- untested latent bug, since that
      branch has never run with multimap set; not fixed here (out of scope,
      genome-BAM path unaffected since multimap stays empty there), just
      flagged for awareness.
    - Real-data validation of the final counts: P-site/CDS counts came out
      to 6.4-8.4% of plain featureCounts' totals, consistently across all 4
      samples. Investigated whether this was still a bug (asked, user said
      dig further) -- three independent signals confirmed it's a real,
      explained dataset property, not a bug: (1) only ~12.8% of
      genome-mapped reads produce ANY transcriptome-space alignment at all
      (STAR's --quantMode TranscriptomeSAM can't represent intronic/
      unspliced-incompatible reads); (2) RSeQC's own already-computed
      read_distribution.txt (completely independent of STAR's transcriptome
      BAM, computed from the genome BAM + BED12) shows ~45.6% of this
      library's tags are INTRONIC (27.67M of 60.62M total tags for
      ribo_untr_a) -- mechanically excluding nearly half the data from
      transcriptome-space by construction; (3) riboWaltz's own in_frame_pct
      stat (from the unmodified, already-verified ribowaltz_psite.R) is
      only ~37-44% for this dataset, so most of what DOES survive
      transcriptome-alignment is further cut by the in-frame-CDS
      restriction. ~13% x ~40% ~= 5%, in the right ballpark for the
      observed ~7% ratio. User accepted this as correct and expected for
      this real (known messy -- rRNA/intron contamination already surfaced
      throughout Phase 1) dataset, not a pipeline defect.

workflow/scripts/psite_cds_counts.R (new)
    - loads the filtered transcriptome bams + persisted annotation_dt/
      psite_offset, reruns bamtolist()/psite_info() on the filtered reads

      re-running psite() itself), then calls riboWaltz's cds_coverage()

      ID/gene_name/biotype/count, so Chr/Start/End/Strand/Length just need
      to be present, not semantically exact, for this to be a true
      drop-in.

RNA-seq arm (GSE202881_shPKM_rna, workflow/star.smk) -- hit a genuine
clumpify HANG on real data, root-caused and fixed 2026-10-18:
--------------------------------------------------------------------------
Symptom: the RNAseq driver job (24h) timed out with only 23/56 steps done.
Checked for orphaned sub-jobs first (per [[snakemake-cluster-cancel]] --
scancel on a driver doesn't cancel its already-submitted sub-jobs) --
squeue was clear, so no collision risk, safe to investigate/resubmit.
sacct showed 2 of the 4 clumpify sub-jobs (mrna_shPKM_C, mrna_shCtrl_C)
hit an 8h TIMEOUT exactly, MaxRSS only ~18.4GB (genuinely a time problem,
not memory). Resumed incrementally once (bumped cluster.yaml's clumpify
entry + the driver's own walltime to 24h/48h, both in the repo template
AND this project), but the SAME two samples then ran 13+ hours with ZERO
bytes written to their output file and near-zero CPU usage (confirmed via
direct ssh+ps on the compute node: process state "S" sleeping, VmSwap 0,
node had 207GB free -- genuinely stalled, not just slow, and not a memory/
swap issue). Bumping time limits further would not have helped.

Root cause had THREE contributing factors, found incrementally by actually
re-checking each fix against real data rather than assuming success:

1. lowcomplexity=t: isolated via direct side-by-side testing (not guessed)
   -- neither raw SRA-style read headers (@SRR....N length=100, vs
   standard Illumina format) nor file size were the cause; subset tests
   (first 20M reads, second ~22M reads, each alone) all completed in ~2
   minutes regardless of header format or the lowcomplexity setting. Only
   the FULL file (41.7M reads) with lowcomplexity=t hung; the SAME full
   file with lowcomplexity=f completed in 5 minutes via a bare manual
   clumpify.sh invocation. Explained by this library's prep (Diagenode
   CATS RNA-seq Kit v2, template-switching-based): raw reads show a
   massive excess of 5' G/C-run sequence (e.g. "GGGGGG" as the single
   most common 6-mer prefix across 100K sampled reads) -- clumpify's
   low-complexity filter has pathological (effectively non-terminating)
   behavior once a duplicate-cluster built from this much near-identical
   low-complexity sequence gets large enough, only at full file scale.

2. threads=1: lowcomplexity=f ALONE was not sufficient -- re-ran for real
   and the same two samples still effectively stalled (CPU time plateaued
   for 90+ minutes while the job stayed alive, confirmed via direct ssh+ps
   on the compute node). Root-caused by comparing the manual test (which
   had used 4 CPU cores, not specified in the rule) against the real
   rule's threads: 1 -- the IDENTICAL clumpify command line against the
   IDENTICAL file completed in minutes with 4 real cores, but stalled
   under threads=1/--cpus-per-task=1. clumpify's JVM spins up worker
   threads based on auto-detected HOST core count, not the actual
   cgroup/SLURM allocation -- with only 1 real core, those threads thrash
   against each other instead of parallelizing.

3. Undersized memory: fixing threads surfaced a THIRD issue -- genuine
   parallelism needs more concurrent memory, not less (each thread needs
   its own buffers). One sample then OOM'd for real (confirmed
   java.lang.OutOfMemoryError in multiple worker threads) at MaxRSS
   18.36GB against the old 15GB-floor-derived -Xmx17g heap.

Fixes: (1) CMD_PARAMS.clumpify set to lowcomplexity=f for this project
specifically (RNAseq_samples.yaml, not the shared repo default -- a real
but dataset-specific pathological interaction, not evidence lowcomplexity=t
is generally wrong; documented the failure mode + a quick diagnostic
command right at the repo template's default instead). (2) workflow/rules/
01a_clumpify.snake: threads bumped 1->4, t={threads} now passed explicitly
to clumpify.sh so its own thread count matches what's actually allocated.
(3) same rule's memory floor bumped 15->24GB. Confirmed fixed end-to-end:
both previously-stalling samples completed in ~3 minutes with comfortable
headroom (MaxRSS 11-12GB against the new ~21.6GB heap) on the real retry.

Also fixed at the repo level (workflow/profiles/Bodhi/cluster.yaml +
workflow/submit_scripts/run_RNAseq_STAR_bodhi.sh), since the TIME-limit
symptom (before the real hang was understood) is a real resource-sizing
gap any RNA-seq project could hit regardless of this specific bug:
clumpify's time limit bumped 8h->24h (same pattern as the existing
sortmerna entry), and the RNAseq driver script's own walltime bumped
24h->48h (needs real margin above any single rule's time limit to survive
the rest of the pipeline afterward).
